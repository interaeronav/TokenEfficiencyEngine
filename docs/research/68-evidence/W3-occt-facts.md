## 1. Drawings (HLR, sections, SVG/DXF)

1. **Exact vs polygonal.** `HLRBRep_Algo` (+`HLRBRep_HLRToShape`) works on the exact BRep; `HLRBRep_PolyAlgo` (+`HLRBRep_PolyHLRToShape`, empty ctor then `.Update(algo)`) works on the shape's *triangulation* and must be pre-meshed. Refman 8.0.1: https://occt3d.com/dev/doc/refman/html/class_h_l_r_b_rep___algo.html , https://occt3d.com/dev/doc/refman/html/class_h_l_r_b_rep___poly_algo.html . FreeCAD TechDraw (`src/Mod/TechDraw/App/GeometryObject.cpp:306-312`) warns: "HLRBRep_PolyAlgo will fail if the whole input shape has not been meshed. meshing the faces is not sufficient." and meshes at 0.10 first.
2. **Outputs** (`HLRBRep_HLRToShape`, https://occt3d.com/dev/doc/refman/html/class_h_l_r_b_rep___h_l_r_to_shape.html): visible `VCompound` (sharp C0), `Rg1LineVCompound` (smooth G1), `RgNLineVCompound` (sewn CN), `OutLineVCompound` (silhouette; `OutLineVCompound3d` 3D), `IsoLineVCompound`; hidden `HCompound`, `Rg1LineHCompound`, `RgNLineHCompound`, `OutLineHCompound`, `IsoLineHCompound`; generic `CompoundOfEdges(type, visible, In3d)`. TechDraw extracts all ten (`GeometryObject.cpp:170-229`).
3. **Measured (local OCP 7.9.3, filleted 120×80×10 plate with 12 holes, 96 fillets):** exact HLR 0.021 s vs PolyAlgo 0.007 s (+0.010 s meshing); 6 stacked plates 0.125 s vs 0.062 s. Poly output fragments (771 outline / 1062 smooth polyline edges vs 48 / 90 exact). After filleting every edge, `VCompound` was **empty** — all tangent edges land in `Rg1LineVCompound`; drawing code that reads only `VCompound` draws nothing.
4. **Section views.** `BRepAlgoAPI_Section` (https://occt3d.com/dev/doc/refman/html/class_b_rep_algo_a_p_i___section.html) returns only vertices+edges (ctors Shape/Shape, Shape/`gp_Pln`, Shape/`Geom_Surface`; `ComputePCurveOn1/2`, `Approximation`, `HasAncestorFaceOn1/2`). For a hatched section face use cut-then-HLR as TechDraw does: `DrawViewSection.cpp:605-619` builds the tool as `BRepBuilderAPI_MakeFace(pln, ±size)` → `BRepPrimAPI_MakePrism(face, size*normal)` (a half-space box), cuts with `FCBRepAlgoAPI_Cut` (l.525), and finds section faces as planar faces of the result whose plane contains the section plane's location with parallel axis (l.718-760). cadquery `Workplane.section()` = `Face.makePlane` + `intersect` (`BRepAlgoAPI_Common`) (`cadquery/cq.py:4315-4331`); build123d `section()` = `Face.make_rect` on plane + `to_section.intersect(plane)` (`operations_part.py:592-665`).
5. **cadquery SVG** (`cadquery/occ_impl/exporters/svg.py:9-203`): `HLRBRep_Algo` + `HLRAlgo_Projector(gp_Ax2[, focus])` + `HLRBRep_HLRToShape`; every edge is discretised with `GCPnts_QuasiUniformDeflection` (`DISCRETIZATION_TOLERANCE = 1e-3`) into `M`/`L` polylines — **no native SVG arcs**. Options: width/height 800×240, projectionDir (-1.75,1.1,5), showHidden, strokeWidth, focus. https://raw.githubusercontent.com/CadQuery/cadquery/master/cadquery/occ_impl/exporters/svg.py
6. **cadquery DXF** (`exporters/dxf.py`): LINE → `_dxf_line`; CIRCLE → `CIRCLE` if closed else `ARC`; ELLIPSE → `ELLIPSE` (center, major_axis, ratio, start/end_param); BSPLINE → `GeomConvert.CurveToBSplineCurve_s` + `SplitBSplineCurve_s` (`CURVE_TOLERANCE = 1e-9`) → control points/order/knots/weights → `ezdxf.math.BSpline` → `msp.add_spline()`; `approx=None|"spline"|"arc"` (`toSplines()`/`toArcs(tolerance=1e-3)`). https://raw.githubusercontent.com/CadQuery/cadquery/master/cadquery/occ_impl/exporters/dxf.py
7. **build123d** (`src/build123d/exporters.py:57-140`, class `Drawing`): `HLRBRep_Algo`, `HLRAlgo_Projector(coordinate_system[, focus])`; visible = `VCompound` + `Rg1LineVCompound` + `OutLineVCompound`; hidden = `HCompound` + `OutLineHCompound` (RgN/Iso not used). `ExportSVG` uses **svgpathtools** (`PT.Line`, `PT.Arc` for circles/ellipses, B-splines → `GeomConvert_BSplineCurveToBezierCurve` → `PT.CubicBezier`/`QuadraticBezier`); `ExportDXF` uses ezdxf `add_line/add_arc/add_circle/add_ellipse/add_spline` with `GeomConvert.SplitBSplineCurve_s(..., PARAMETRIC_TOLERANCE)`; 26+ ANSI/ISO linetypes. `ocpsvg` (Apache-2.0, https://github.com/snoyer/ocpsvg) is an SVG-path↔edge/wire/face converter and a build123d dependency but is **not** used by `ExportSVG`. https://raw.githubusercontent.com/gumyr/build123d/dev/src/build123d/exporters.py

## 5. Topological naming

32. **Problem.** Parametric features reference sub-shapes (faces/edges) of earlier results; OCCT identifies sub-shapes only by `TShape` pointer + index in the current explorer order, so any upstream edit that changes face count/order silently re-targets or breaks downstream references (fillet on "face 7"). Ondsel: "the toponaming problem is an inherent side effect of parametric modeling… later features depending on the geometry from earlier steps" (https://www.ondsel.com/blog/toponaming-problem-is-history/).
33. **OCCT offers** (a) per-operation history on every `BRepBuilderAPI_MakeShape`/`BRepAlgoAPI_*`: `Generated(S)`, `Modified(S)`, `IsDeleted(S)`, `History()` → `BRepTools_History` (tracks **vertex, edge, face, solid** only; `AddGenerated/AddModified/Remove/Merge/IsSupportedType`) https://occt3d.com/dev/doc/refman/html/class_b_rep_tools___history.html ; (b) OCAF `TNaming`: `TNaming_Builder(label).Generated(old,new)/Modified(old,new)/Delete(old)/Select`, evolutions `PRIMITIVE/GENERATED/MODIFY/DELETE/SELECTED`, `TNaming_Selector.Select(selection, context)` + `Solve()` to re-resolve after regeneration, `TNaming_Tool.GetShape/CurrentShape/NamedShape`, results stored "in linear order under the Result Label" https://occt3d.com/dev/doc/overview/html/occt_user_guides__ocaf.html , https://occt3d.com/dev/doc/refman/html/class_t_naming___selector.html (all bound: `OCP.TNaming`, `OCP.TDF`, `OCP.TDataStd`). 7.9.3 fixed a `TNaming_UsedShapes` bug.
34. **cadquery**: string grammar `>Z <Z >>Z <<Z |Z #Z +Z -Z %PLANE %CIRCLE… >Z[-2] and/or/not/exc`, classes `NearestToPointSelector, BoxSelector, ParallelDirSelector, DirectionSelector, PerpendicularDirSelector, TypeSelector, RadiusNthSelector, CenterNthSelector, DirectionMinMaxSelector, DirectionNthSelector, LengthNthSelector, AreaNthSelector, And/Sum/Subtract/InverseSelector, StringSyntaxSelector` (https://raw.githubusercontent.com/CadQuery/cadquery/master/cadquery/selectors.py). Docs limitation: "Non-linear edges are not selected for any string selectors except type (%) and center (>>)" (https://cadquery.readthedocs.io/en/latest/selectors.html). Selectors re-run on current geometry; nothing persists. Internally cadquery already consumes `builder.IsDeleted/Generated/Modified` (`shapes.py:5792-5804`, `6056`) and 2.7 added "bidirectional mapping of subshapes" (changes.md).
35. **build123d**: `ShapeList.filter_by/sort_by/group_by/filter_by_position`, operators `> < >> << | []`, enums `Axis, SortBy(LENGTH,RADIUS,AREA,VOLUME,DISTANCE), GeomType`, and `Select.ALL/LAST` ("LAST selects features created or altered by the most recent operation"). Stance (tutorial_selectors.html): "We've also avoided the classic CAD 'Topological naming problem' by never referring to features with names or tags that could become obsolete as the part changes." Joints are named (`part.joints["label"]`) but are Locations, not sub-shape references.
36. **FreeCAD 1.0.0** (GitHub release, 2024-11-19): "the inclusion of the topological naming problem mitigation code." Code: `src/App/ElementMap.{h,cpp}` (IndexedName ↔ MappedName; `setElementName`, `encodeElementName(type, postfix, tag)`, `hashElementName`/`dehashElementName` via `StringHasher`; SPDX `LGPL-2.1-or-later`, © realthunder 2018-2022), `ElementNamingUtils.{h,cpp}` (`ELEMENT_MAP_PREFIX=";"`, `POSTFIX_TAG=";:H"`, `POSTFIX_MOD=";:M"`, `POSTFIX_GEN=";:G"`, `POSTFIX_MODGEN=";:MG"`, `POSTFIX_INDEX=";:I"`, `MISSING_PREFIX="?"`), `MappedName`, `IndexedName`, `MappedElement`, `StringHasher`, `ComplexGeoData`; `src/Mod/Part/App/TopoShape*.cpp`, `TopoShapeExpansion.cpp`, `TopoShapeMapper`, `TopoShapeOpCode.h` (Version 15; `FUS CUT CMN SEC XTR RVL FLT CHF THK OFS LFT SWP PSH SLC DFT HSP SPT MIR SKT …`). Name format (realthunder wiki): `Face6;:M2;FUS;:T1:5:F` = Face6 modified (M, index 2) by fuse from tag-1 shape; multi-source `Face6;:M(Face2;:T2:5:F);FUS;:T1:5:F`; hashed `#a8;:M#a7;RFI;:T2:2:F`; history decoded by `getElementHistory()` https://github.com/realthunder/FreeCAD_assembly3/wiki/Topological-Naming-Algorithm . Ondsel: performance "negligible"; "TNP mitigation helps only for a specific kind of model breakage."
37. **Recommended scheme for a headless kernel:** (i) every feature op records `BRepTools_History` (merge per feature) and assigns each result sub-shape a **semantic name** `feature_id.role[.k]` (e.g. `boss3.top`, `hole7.wall`, `fillet2.face[0]`) derived from `Generated`/`Modified` of named inputs, exactly FreeCAD's `source;op;tag` idea but with roles instead of indices; (ii) attach a **geometric fingerprint** per sub-shape (surface type, quantised centroid/normal/area or curve type/length/midpoint, in model units, rounded to tolerance) as tie-breaker and fallback when history is ambiguous (multiple `Generated`) or empty (imported STEP); (iii) on re-evaluation resolve a reference by history first, fingerprint second, and otherwise **fail loud** with the nearest candidates; (iv) never persist explorer indices; (v) expose build123d-style selectors only as a *query* layer that materialises to names. Do not use `TNaming`/OCAF unless you also adopt TDocStd persistence — history maps + your own store are cheaper and already bound.

## 6. Assembly solving

38. cadquery `occ_impl/solver.py` imports **`casadi as ca`** and uses `ca.Opti` with `"ipopt"` (changes.md v2.2: "Switch to Casadi and iPOPT for assembly solver [#1063]"; `nlopt` is still a declared dependency but not the solver). Kinds: `UnaryConstraintKind = Literal["Fixed","FixedPoint","FixedAxis","FixedRotation"]`, `BinaryConstraintKind = Literal["Plane","Point","Axis","PointInPlane","PointOnLine"]`; poses `DOF6 = ((tx,ty,tz),(a,b,c))` with a 3-parameter rotation built from `gp_Quaternion`; costs are squared residuals (`ca.sumsqr`); `TOL=1e-12`, `DIFF_EPS=1e-10`, ipopt `tol 1e-14`. Docs cost functions: Point `(param-|c1-c2|)²`, Axis `(k·(param - d1∠d2))²` (param default 180°), Plane = Point+Axis, PointInPlane `dist(c,p_offset)²`, PointOnLine `(param-dist(c,l))²`, FixedPoint `||c-param||²`, FixedRotation, FixedAxis `(a∠param)²`; no DOF report or over/under-constraint diagnostics (https://cadquery.readthedocs.io/en/latest/assy.html). **casadi is LGPL-3.0+** (PyPI 3.8.0), the "+LGPL-3.0 dep" in `CLAUDE_A45_SCRIPT.md:72`.
39. build123d `joints.py`: `RigidJoint(label, to_part, joint_location)`, `RevoluteJoint(label, to_part, axis, angle_reference, angular_range)`, `LinearJoint(label, to_part, axis, linear_range)`, `CylindricalJoint(…)`, `BallJoint(label, to_part, joint_location, angular_range, angle_reference)`; `connect_to()`/`relative_to()` compute a `Location` (`relative_axis.location * rotation * other.relative_location.inverse()`) and move the child — declarative placement, **no solver, no DOF tracking**; ranges only validate parameters. https://raw.githubusercontent.com/gumyr/build123d/dev/src/build123d/joints.py
40. **scipy replacement is reasonable.** `scipy.optimize.least_squares(fun, x0, jac, bounds, method='trf'|'dogbox'|'lm', ftol/xtol/gtol=1e-8, x_scale, loss)` returns `x, cost, fun, jac, grad, optimality, nfev, status` where `jac` is the (modified) Jacobian at the solution, usable for rank (https://docs.scipy.org/doc/scipy/reference/generated/scipy.optimize.least_squares.html). Model each part as 6 DOF (translation + unit quaternion with a `|q|²-1` residual, or rotation vector to stay at 6 params), residuals per constraint as in cadquery's cost list, `DOF = 6n − rank(J)` (numpy `matrix_rank` with tolerance), over-constraint = inconsistent residual > tol. Licence: scipy BSD vs casadi LGPL-3.0+; only x_scale/robust loss needs care for mm-vs-radian scaling.

## 7. Sheet metal

41. **FreeCAD SheetMetal** https://github.com/shaise/FreeCAD_SheetMetal — repo `LGPL-2.1`. `SheetMetalUnfolder.py` (© 2014-2018 Ulrich Brammer, LGPL-2+): user picks a base face; `SheetTree` measures thickness by a ray, `Bend_analysis()` walks face adjacency building `Simple_node`s with `node_type "Flat"|"Bend"` (`"<Cylinder object>" in face.Surface`), `c_face_idx` counter-face, bend `axis`, direction up/down; neutral-fibre length `_trans_length = (innerRadius + k_Factor*thickness) * bend_angle`; K-factor from a lookup keyed by `innerRadius/thickness`; `KFACTORSTANDARD "ansi"` → k, `"din"` → k/2. `SheetMetalNewUnfolder.py` (© 2025 Alex Neufeld, LGPL-2.1+) rebuilds it on a **networkx** face graph with `KFactorStandard.ANSI|DIN`. LGPL means dynamic use/port with attribution is fine; copying code into an Apache/MIT kernel is not.
42. **Flat-first alternative** (permissive, no unfolder needed): define the flat pattern (2D outline + bend lines with angle, inner radius r, K) and *fold*: split the flat at each bend line, keep a strip of width BA, replace it by a cylindrical face pair of inner radius r (arc length BA at the neutral axis), and rotate the outboard flange rigidly about the bend axis; the folded solid and the flat are then the same parametric object, and the derived quantity is the flat length, never an unfold search. This is exactly the inverse of the Brammer walk.
43. **Bend allowance, citable:** `BA = A·(π/180)·(R + K·T)` (A bend angle °, R inside radius, K = t/T neutral-axis ratio, T thickness), outside setback `OSSB = (R+T)·tan(A/2)`, `BD = 2·OSSB − BA`; K "typically between 0.3 and 0.5" — Wikipedia "Bending (metalworking)", CC BY-SA 4.0, citing *Manufacturing Processes Reference Guide*, Industrial Press 1994 (https://en.wikipedia.org/wiki/Bending_(metalworking)). **DIN 6935** (German practice; primary text paywalled) uses developed length `L = a + b + v` with compensation value `v` and correction factor `k = 0.65 + 0.5·log10(r/s)` for r/s ≤ 5, `k = 1` for r/s > 5 (https://www.modulusmetal.com/din-6935-cold-bending-of-flat-rolled-steel/); "DIN 6935's k is NOT the American 'K-factor'" (https://www.mechanixcalc.com/standards/din-6935) — which is why SheetMetalUnfolder halves it. Machinery's Handbook is not freely citable online; the Wikipedia/Industrial Press citation suffices.

## 9. Units — scale traps

47. OCCT geometry is unit-less; STEP/IGES writers *declare* `write.step.unit`/`write.iges.unit` (default MM) and readers scale into `xstep.cascade.unit` (MM). XCAF documents may carry `XCAFDoc_LengthUnit` via `XCAFDoc_DocumentTool::SetLengthUnit(doc, value)` — value is **"in meter"** (0.001 = mm) — and `GetLengthUnit` (https://occt3d.com/dev/doc/refman/html/class_x_c_a_f_doc___document_tool.html); STEPCAF writer honours it (fact 9).
48. glTF 2.0 spec: "glTF uses a right-handed coordinate system", "The units for all linear distances are meters", "After applying the node's global transform, mesh vertex position values are meters" (`specification/2.0/Specification.adoc` l.706/713/1732, https://github.com/KhronosGroup/glTF). `RWMesh_CoordinateSystemConverter` input/output length units are scale-to-metres factors, default `-1` = **no conversion** (https://occt3d.com/dev/doc/refman/html/class_r_w_mesh___coordinate_system_converter.html). Consequences: **cadquery `exportGLTF/exportGLB`** never sets `XCAFDoc_LengthUnit` (grep: no `LengthUnit` anywhere in the installed cadquery 2.8.0) so a 10 mm part is written as 10 glTF units = 10 m (it does rotate `Location((0,0,0),(1,0,0),-90)` for Y-up, `exporters/assembly.py:464-468`); **build123d `export_gltf`** sets `SetLengthUnit_s(doc, 1/UNITS_PER_METER[unit])` and is correct. STL/OBJ carry no unit; 3MF has a `unit` attribute (cadquery writes "millimeter").

## What NOT to assume

- That `occt3d.com/dev/doc` describes 7.9 — it is 8.0.1; e.g. it says `write.step.schema` default AP214CD, 7.9.3 runtime says **AP214IS**.
- That the OCP wheel binds every OCCT toolkit it ships: `TKDEOBJ`/`TKDEPLY` are linked, `OCP.RWObj`/`OCP.RWPly` do not exist (write OBJ/PLY yourself or via trimesh).
- That `import OCP` is VTK-free: the .so links nine VTK dylibs; only `cadquery-ocp-novtk` is.
- That `RWGltf_CafWriter` scales mm→m: it does so **only** if the XCAF doc carries `XCAFDoc_LengthUnit`; cadquery never sets it.
- That `VCompound` is "the visible edges": on filleted/tangent models the lines are in `Rg1LineVCompound`/`OutLineVCompound`.
- That `HLRBRep_PolyAlgo` accepts an unmeshed shape or gives clean arcs — it needs a whole-shape mesh and returns polylines.
- That `BRepFeat_MakeCylindricalHole` does counterbores/countersinks, or that either library uses it (both subtract primitives).
- That `BRepBndLib::Add` gives a tight box — it is enlarged by tolerances; use `AddOptimal` (both libs default to it, cadquery only when `tol` is passed).
- That `BRepMesh` output is documented as deterministic under `InParallel` — it is not documented; it *was* bit-identical in the local test; put a hash test in CI rather than a belief in the design. And build123d's `tolerance` is a **relative** deflection.
- That cadquery's assembly solver is nlopt — it is casadi (LGPL-3.0+) + IPOPT since 2.2; nlopt is a vestigial dependency.
- That build123d Joints solve anything — they are declarative Locations; there is no DOF model.
- That build123d has threads/IsoThread — they are in `bd_warehouse.thread` (Apache-2.0).
- That FreeCAD's toponaming code or SheetMetal/Fasteners data can be vendored: FreeCAD core is LGPL-2.1-or-later, SheetMetal LGPL-2.1, Fasteners **GPL-2.0**; take the *scheme* (op-code + source + tag naming, hashed) not the code, and take fastener/clearance/tap numbers from bd_warehouse (Apache-2.0).
- That `BRepTools_History` tracks wires/shells — only vertex, edge, face, solid.
- That the OCCT 7.9.x series is old: 7.9.0 2025-02-18, 7.9.1 2025-05-21, 7.9.2 2025-10-18 (C++17), 7.9.3 2025-12-06; 8.0.0 2026-05-07, 8.0.1 2026-07-30; OCP master already targets 8.0.0.1 while cadquery 2.8.0 pins `cadquery-ocp<8.0,>=7.9.3.1` (repo on GitHub shows licence NOASSERTION; PyPI/README say Apache-2.0).
- That the 140 s first import is Python compiling OCP — measured compile cost of the whole closure is 0.5 s; the cause is native first-load and is unmeasured cold.
