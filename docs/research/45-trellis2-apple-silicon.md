## trellis-mac: architecture — patch layer, not a fork

- It is NOT a fork of the TRELLIS.2 tree. The repo contains only `backends/`, `patches/`, `generate.py`, `setup.sh` (~15 files). `setup.sh:47-52` clones `microsoft/TRELLIS.2` (depth 1, **unpinned main HEAD**) at install time; `patches/mps_compat.py` then rewrites 7 upstream files in-place via string replacement.
- Tracking risk: every patch is `src.replace(old, new)` with an "already patched" guard but **no assertion that the pattern matched** — if upstream drifts, a patch silently no-ops and writes the file unchanged (`patches/mps_compat.py`, all `patch_*` functions). Combined with the unpinned clone, an upstream push can break installs invisibly.
- Files patched: `sparse/config.py` (adds `sdpa`/`naive` to allowed sparse-attn backends — upstream only allows xformers/flash_attn/flash_attn_3; upstream's dense `modules/attention/config.py` already allows sdpa), `sparse/attention/full_attn.py`, `image_feature_extractor.py`, `pipelines/rembg/BiRefNet.py`, `representations/mesh/base.py`, `models/sc_vaes/fdg_vae.py`, `pipelines/trellis2_image_to_3d.py`, `pipelines/base.py` (`.cuda()` → mps-aware). Plus stub packages for `cumesh`, `flex_gemm`, `nvdiffrast`, `o_voxel` (`backends/stubs.py`).

## CUDA→MPS substitution inventory (with correctness compromises)

- **Sparse conv (`flex_gemm`)** → two paths: (a) default `mtlgemm` (Metal flex_gemm fork by pedronaugusto) since its "zero-copy MPS, real fp16/bf16 kernels, real masked implicit GEMM, no per-call waitUntilCompleted" fixes (README.md:140); (b) fallback `backends/conv_none.py` — pure-PyTorch gather-scatter submanifold conv, Python-dict spatial hash built on CPU, neighbor maps cached per-tensor; **stride=1 only, `SparseInverseConv3d` raises NotImplementedError** (conv_none.py:17-19,128-133). Safe for TRELLIS.2: all model convs are kernel-3/stride-1; up/downsampling is spatial2channel, not strided conv (`sc_vaes/sparse_unet_vae.py:34-52`). Fallback measured "~10x slower than CUDA flex_gemm" (issue #1). mtlgemm's metallib is MSL 4.0 → **loads only on macOS 26+**; older macOS falls back to conv_none (generate.py:22-28).
- **Fused sparse attention (`flash_attn` varlen)** → padded SDPA: variable-length sequences zero-padded into a dense batch, `F.scaled_dot_product_attention`, unpadded via Python loop (mps_compat.py:54-90). Correctness wrinkle: the patch does not mask padding, so zero-vector padded keys still contribute exp(0)-weighted attention mass — a real approximation; UNVERIFIED whether outputs materially diverge from flash_attn varlen. Perf: the dominant remaining bottleneck (~80 s of a 5m13s run — README.md:151).
- **`nvdiffrast`** → `mtldiffrast` (Metal) inside pedronaugusto's `o_voxel.postprocess.to_glb`, else the pure-Python fallback baker `backends/texture_baker.py` (xatlas UV unwrap + numpy UV rasterizer + scipy cKDTree k-NN inverse-distance sampling at native 512 res). Fallback ~15 s vs ~11 s Metal, softer chart boundaries (README.md:146).
- **`cumesh` (hole fill / remove_faces / simplify at decode)** → **unconditionally skipped** — patched to `return` immediately because the Metal cumesh port segfaults on decoder-sized (~800K-face) meshes (mps_compat.py:234-296). Consequence: output meshes may have small holes (README.md:150). The mesh is instead decimated 858K→200K faces via `fast_simplification` before baking, because `mtlbvh`'s builder is unstable on 800K+ face inputs (README.md:120, generate.py:206-217).
- **`o_voxel._C` hashmap mesh extraction** → `backends/mesh_extract.py`: pure-Python dict rebuild of `flexible_dual_grid_to_mesh` (quad building + normal-alignment triangulation), forced over any installed o_voxel because the Metal port's `convert` also segfaults (mps_compat.py:299-330). ~8 s, inference-only (`train=True` raises). Claims "identical output to the CUDA version for inference" (mesh_extract.py:5) — UNVERIFIED numerically.
- **Misc**: `PYTORCH_ENABLE_MPS_FALLBACK=1` required before torch import — `segment_reduce` and "a few other ops" otherwise crash instead of CPU-falling-back (generate.py:12-15). `torch.cuda.empty_cache()` guarded; DINOv3 HF layer-structure fix included.

## mtldiffrast & the pedronaugusto Metal stack

- All separate pip packages (built from source, `--no-build-isolation`, need the Xcode Metal Toolchain; `MACOSX_DEPLOYMENT_TARGET>=12` — setup.sh:84-113), all MIT, all single-author (pedronaugusto):
  - `mtldiffrast`: MSL implementation of nvdiffrast's four ops — rasterize, interpolate, texture (mip/nearest/linear/trilinear), antialias — with torch.autograd backward and zero-copy MPS/CPU tensor binding via unified memory; claims "API-compatible with nvdiffrast for drop-in use". 3 stars, 9 commits. Numerics parity vs nvdiffrast: UNVERIFIED.
  - `mtlgemm` (fork of FlexGEMM): Metal sparse submanifold conv3d — explicit/implicit/masked-implicit GEMM + split-K, FlexGEMM-compatible API, also provides the `grid_sample_3d` the baker prefers. 77 commits, 2 stars; fp16/bf16 shader specializations partly "deferred to follow-up work".
  - `mtlbvh` (cubvh-compatible): 4-wide BVH, closest-point/SDF/ray ops, zero-copy. 11 commits; unstable on 800K+ face builds.
  - `mtlmesh` (cumesh Metal port): cleaning, decimation, hole filling, UV unwrap (clustering + xatlas), narrow-band-UDF dual-contouring remesh; runtime CUDA/Metal auto-select. 59 commits — but trellis-mac found it segfaults on decode-size meshes.
  - `trellis2-apple`: full fork of microsoft/TRELLIS.2 (34 stars, 28 commits) whose `o-voxel` CPU/Metal fork supplies `postprocess.to_glb`; also contains a real `mlx_backend/` (see MLX section).

## PyTorch MPS state — stable = 2.13.0, released 2026-07-08

(pytorch.org/blog/pytorch-2-13-release-blog/, github.com/pytorch/pytorch/releases)

- **FlexAttention landed on MPS in 2.13**: hand-written Metal kernels for sparse prefill + decode paths, GQA, captured buffers; ~12.3x over SDPA at 0.8%-density sliding-window (32K seq), ~4.15x at 8K/64-window; dense patterns still favor SDPA. "API Unstable". The single most relevant upstream change for the padded-SDPA bottleneck (document/varlen masking expresses TRELLIS's variable-length sparse batches without padding waste).
- **Large op migration MPSGraph → native Metal kernels** in 2.13 (copy/cast, RNG, comparisons, sum/mean reductions, cumsum, sort, embedding backward, scatter/gather) — cuts per-dispatch overhead. 2.11 had "Comprehensive Operator Expansion" for MPS; 2.12 made **all MPS tensors unified-memory allocated** (CPU can read without copies).
- **torch.compile on MPS**: still effectively prototype — tracker issue #150121 targeted "tentative beta" at 2.8 but 2026 issues show invalid generated Metal shaders on reductions, backward-pass failures, and wrong results on some pooled ops (issues #152155, #161905, #169738). Do not build on it; eager + FlexAttention + custom kernels is the realistic stack. `torch.mps.compile_shader` (inline MSL) and `_mps_loadMetallib` (PR #177276) exist for custom kernel injection.
- **dtypes**: fp16 native; bf16 supported on Apple Silicon with macOS 14+ (autocast-bf16 issue #139386 closed; mtlgemm/mps-flash-attn ship bf16 kernels); fp64 unsupported on MPS. macOS 14+ is the MPS floor since torch 2.9/2.12.
- **Unified memory mechanics**: allocator cap = `recommendedMaxWorkingSetSize` × `PYTORCH_MPS_HIGH_WATERMARK_RATIO` (default 1.4 on unified memory; 0.0 disables) (docs.pytorch.org/docs/2.8 mps_environment_variables). On 128 GB, GPU-addressable memory is ~90-100 GB+ before touching the ratio — no VRAM/RAM split, no `.cuda()` staging copies, zero-copy Metal interop (the mtl* stack exploits this).
- **Correctness pitfalls observed in this exact workload**: (1) macOS **GPU watchdog kills long-running Metal kernels silently** — the decoder returns empty tensors, no Python exception; tighter when WindowServer is loaded; workarounds: run headless/SSH, `MTL_CAPTURE_ENABLED=1` extends the timeout (generate.py:98-142, trellis-mac issue #8, M2 Ultra). (2) Silent CPU fallback with `PYTORCH_ENABLE_MPS_FALLBACK=1` hides perf cliffs. (3) Thermal throttling: identical run 3.5 min → 36 min on a hot M4 Pro (README.md:159).

## Measured perf & M5 Max levers

- trellis-mac M4 Pro 24 GB, pipeline `512`, 12 steps/stage, Metal stack, cool machine (README.md:124-146): pipeline load 103 s (once per process); sparse-structure sampling 80 s (attention-bound); shape-SLat sampling 22 s; tex-SLat sampling 12 s; shape VAE decode ~20 s; tex VAE decode ~7 s; dual-grid→mesh (pure Python) ~8 s; simplify ~1 s; Metal bake 1024² ~15 s. Total cold 5m13s; generation+bake 3m20s. Peak memory ~18 GB. mtlgemm fixes made the VAE decoders 2.5-2.9x faster (38 s→27 s).
- Upstream CUDA floor: "NVIDIA GPU with at least 24GB" (README.md:60). H100 reference: ~3 s at 512³, ~17 s at 1024³ — Apple Silicon is and will stay ~1-2 orders slower than H100, but far under the 24 GB constraint's ceiling for resolution.
- M5 Max (2026 MacBook Pro): 40-core GPU **with per-core Neural Accelerators**, 614 GB/s bandwidth (2.25x M4 Pro's 273), up to 128 GB (support.apple.com/en-us/126319, everymac.com). Realistic engine targets (estimate, UNVERIFIED until benchmarked): 2-3x raw over M4 Pro → ~1:10-1:40 generation+bake at 512; FlexAttention-MPS could cut the 80 s sampling stage several-fold more; the 16" Max chassis throttles far less. 128 GB headroom enables `1024`/`1024_cascade` pipelines, 2048² textures, batch-of-N queued jobs, and keeping pipeline+DINOv3+RMBG resident (kills the 103 s per-process load — decisive for a resident MCP-server product).

## Quantization: GGUF exists but not for the PyTorch path

- Community GGUF: `ilintar/trellis2-gguf` (HF) — Q4/Q8 of the full component set, consumed by **`pwilkin/trellis.cpp`** — a complete C++/GGML reimplementation (flow transformers, VAEs, dual-contour mesh extraction, UV/texture bake, GLB export; 262 stars). Backends: **CUDA, Vulkan, ROCm — no Metal backend documented, no macOS support claimed**; runs 1024-cascade in ~16 GB VRAM. So GGUF builds do NOT plug into PyTorch/MPS; they matter only if we adopted/ported the GGML runtime (ggml has a Metal backend generally — porting cost UNVERIFIED).
- PyTorch-path quantization on MPS: torchao int8/int4 weight-only works on MPS; int4 is ~1.9x slower than int8 there (bit-unpacking, no native 4-bit in Metal) → int8-weight-only is the sane MPS option. On a 128 GB machine quantization is a bandwidth play, not a capacity necessity.

## MLX / Metal ecosystem

- **`pedronaugusto/trellis2-apple` contains a genuine MLX backend** (`mlx_backend/`: attention, transformer blocks, rope, sparse tensors/ops/conv, VAE blocks/decoders, dinov3, flow models, structure decoder, pipeline, convert, app_mlx) — the diffusion transformers and VAEs re-expressed in MLX, not just Metal postprocessing. **No published Apple-hardware perf numbers; completeness/correctness UNVERIFIED.** The only MLX TRELLIS port found.
- Third-party Metal attention: `mps-flash-attn` (PyPI; github.com/imperatormk/mps-flash-attention, MIT, 53 commits): O(N)-memory flash attention Metal kernels, fp16/bf16/fp32, causal + sliding-window, avg ~1.8x over SDPA, torch 2.5-2.11, no dropout; varlen support undocumented.
- Metal kernel authoring cost for the two hot spots: **sparse attention — likely avoidable** (FlexAttention-MPS in torch 2.13 covers block-sparse/varlen masking with hand-tuned Metal kernels); **sparse conv — already solved by vendoring mtlgemm**; a from-scratch fused gather-GEMM-scatter kernel was scoped in trellis-mac issue #1 (single-dispatch fused kernel via `torch.mps.compile_shader`, est. 3-5x on that layer) but mtlgemm's fixes already made it the default path.

## Sustainability / bus factor

- trellis-mac: effectively **bus factor 1** — 24 commits, all in a 9-day burst 2026-04-19→04-28 by shivampkumar (one outside PR), **zero commits since April 28** as of 2026-08-22. 465 stars, 32 forks, 4 open issues. MIT (porting code only; DINOv3 is Meta gated license, RMBG-2.0 is **CC BY-NC — commercial use needs a BRIA license**, README.md:161-168).
- pedronaugusto Metal stack: also single-author, tiny star counts (1-4) but real commit depth (mtlgemm 77, mtlmesh 59); "deferred perf items" tracked cross-repo. No org backing on either author. Treat both as upstream-frozen snapshots, not dependencies with a support horizon.

## Implications for the build

- **Fork the tree, don't replay string patches.** trellis-mac proves the port surface is small (7 files + 4 subsystems) but its unpinned-clone + silent-no-op patch mechanism is unshippable. The product hard-forks upstream 75fbf01 with a device-abstraction layer (`cuda`/`mps` runtime dispatch), keeping the CUDA path a first-class CI target.
- **Vendor the pedronaugusto stack (MIT) rather than re-implement**: mtlgemm (sparse conv + grid_sample), mtldiffrast, mtlbvh, mtlmesh — but pin, import the sources into our repo, and own the bugs: each is bus-factor-1, and two known crashers (mtlmesh/cumesh on 800K-face meshes, mtlbvh builder instability) need fixing in-tree rather than working around via the forced 200K-face decimation that currently costs output fidelity.
- **Attention is the #1 perf lever**: replace the padded-SDPA sparse-attention shim with FlexAttention-on-MPS (torch >= 2.13, document-mask pattern for varlen batches). This also removes the unmasked-padding correctness wrinkle. Keep SDPA as fallback for dense/small shapes; ignore torch.compile-on-MPS for now (prototype, miscompiles reductions).
- **Design for residency**: 103 s of the 5m13s is per-process pipeline load. An MCP-server product keeps weights resident in unified memory (128 GB >> 18 GB peak) — instant warm generations, plus room for 1024-cascade, 2048² textures, and concurrent jobs the 24 GB CUDA floor can't touch.
- **Ship watchdog + thermal telemetry**: detect the GPU-watchdog empty-mesh signature and throttle-aware timing (both burned trellis-mac users), report them as structured one-line agent-consumable errors — TEE's fail-loud-and-cheap rule applied.
- **Precision/quantization plan**: bf16/fp16 eager on MPS (macOS 14+); torchao int8-weight-only as an optional bandwidth lever; skip int4 on MPS; GGUF is irrelevant to the PyTorch path.
- **Watch but don't bet on**: trellis2-apple's MLX backend (full transformer/VAE re-implementation exists, perf/correctness unpublished) as a long-term escape from PyTorch-MPS limits; trellis.cpp-with-Metal as a minimal-footprint runtime; both UNVERIFIED on Apple hardware today.
- **Licensing gate for a product**: RMBG-2.0 (CC BY-NC) must be replaced or licensed for commercial background removal; DINOv3's Meta gated license needs review before shipping weights-adjacent tooling.
