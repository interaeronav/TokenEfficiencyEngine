# Unreal Engine core concepts and object model

**Summary.** Almost everything in Unreal that can be saved, replicated, garbage-collected or seen by a script is a `UObject`. Things that exist *in the world* are `AActor`s; the behaviour and geometry bolted onto them are `UActorComponent`s. A reflection system built by the Unreal Header Tool at compile time exposes classes, properties and functions to Blueprint, Python, the editor's details panel, serialisation and the network — which is why the Python API can call almost anything Blueprint can call without anyone writing Python bindings. Understanding this layer is the difference between scripting Unreal effectively and cargo-culting snippets.

## Key facts

| Concept | What it is | Prefix | Notes |
|---|---|---|---|
| `UObject` | Base class of the reflected object system | `U` | Garbage collected, serialisable, reflected |
| `AActor` | A `UObject` that can be placed or spawned in a level | `A` | Has a transform only via a root `USceneComponent` |
| `UActorComponent` | Reusable behaviour attached to an Actor | `U` | No transform of its own |
| `USceneComponent` | `UActorComponent` with a transform; can be parented | `U` | Basis of the component hierarchy |
| `UPrimitiveComponent` | `USceneComponent` that renders and/or collides | `U` | `UStaticMeshComponent`, `ULightComponent` etc. derive from it |
| `UStruct` / `FStruct` | Value type with reflection and serialisation, **not** garbage collected | `F` | `FVector`, `FTransform`, `FHitResult` |
| `UInterface` | Reflected interface | `I` / `U` | Two classes generated per interface |
| `UEnum` | Reflected enumeration | `E` | |
| `TArray`, `TMap`, `TSet` | Engine container templates | `T` | References inside them are visible to GC |
| `CDO` | Class Default Object — the per-`UClass` template instance | — | Generated by the constructor, thereafter read-only |
| `UHT` | Unreal Header Tool — the reflection code generator | — | Runs before the C++ compiler |

## The UObject system

`UObject` is the root of Unreal's own object model. Deriving from it buys you, per Epic's documentation:

- garbage collection
- automatic reference updating
- reflection
- serialisation
- automatic updating of default property changes
- automatic property initialisation
- automatic editor integration
- runtime type information
- network replication

The cost is a set of rules that C++ programmers coming from outside Unreal reliably break:

- **`UObject`s do not support constructor arguments.** All C++ `UObject`s are initialised at engine startup and the engine calls the default constructor. No default constructor, no compile.
- **Constructors must be lightweight.** Set default values and create default subobjects. Nothing else. Initialisation work belongs in `BeginPlay()` for Actors and Actor Components.
- **Never use `new` or `delete` on a `UObject`.** Use `NewObject<T>()` at runtime and `CreateDefaultSubobject<T>()` inside constructors. Manual memory management corrupts the GC's view of the heap.
- **`UObject`s are zeroed before the constructor runs** — the whole class, `UPROPERTY`s and plain native members alike.

### The UCLASS macro and the CDO

`UCLASS()` associates a C++ class with a runtime `UClass` describing its Unreal type. Each `UClass` owns exactly one **Class Default Object**, a template instance produced by the class constructor and unmodified afterwards. `GetClass()` retrieves the `UClass` for any instance. Treat both as read-only.

The CDO is why the editor can show you default values for a Blueprint you have never instanced, and why changing a default on a parent class propagates: when a CDO changes, the engine attempts to apply the change to loaded instances — if an instance's value still matches the *old* CDO value it is updated to the new one; if it differs, the engine assumes the value was deliberately overridden and leaves it alone.

### Reflection and the Unreal Header Tool

Reflection is not a C++ language feature. Unreal generates it. The Unreal Header Tool preprocesses headers containing `UCLASS`, `USTRUCT`, `UENUM`, `UPROPERTY`, `UFUNCTION` and `UINTERFACE` macros and emits `.generated.h` / `.gen.cpp` files that register type information.

Only members marked with `UPROPERTY` or `UFUNCTION` are listed in the `UCLASS`. A `UObject`-derived class may have plain native members, but the engine cannot see them: they will not serialise, will not appear in the details panel, will not be visible to Blueprint or Python, and will not keep a referenced object alive.

This single fact is the foundation of file `06`. The Python `unreal` module is **not pre-generated** — it reflects whatever is currently exposed to Blueprint in your editor. Enable a plugin and its Blueprint-exposed API appears in Python. Write a `UFUNCTION(BlueprintCallable)` in your project's C++ and it appears in Python. This is also how the Remote Control API and the MCP toolsets work.

### Garbage collection and reference semantics

Unreal uses a mark-and-sweep collector operating over the reflected reference graph. What matters in practice:

- A `UObject*` stored in a `UPROPERTY` or inside an engine container (`TArray`, `TMap`, …) is **visible to GC** and keeps its target alive.
- A `UObject*` stored in a raw pointer is **invisible**: it neither prevents collection nor gets nulled. It becomes a dangling pointer.
- When an `AActor` or `UActorComponent` is destroyed, every reference to it visible to reflection is **automatically nulled**. Null-checking therefore catches both ordinary nulls and would-be dangling pointers.
- For a non-owning reference use `TWeakObjectPtr` — it does not prevent collection, can be queried for validity, and is set to null when the target dies.
- Force-deleting an asset in the editor also nulls referencing `UPROPERTY`s. Any code operating on asset `UObject`s must tolerate this.

Serialisation follows the same graph: every `UProperty` is written and read automatically unless marked `Transient` or unchanged from the CDO default. Added properties get CDO defaults on load; removed properties are silently ignored. This is why an artist can place an Actor, change a value in the details panel, save, and reload without a line of code.

## Actors and components

An `AActor` is a `UObject` that can be placed in or spawned into a level. An Actor by itself has no transform — its position comes from a **root component**, a `USceneComponent` at the top of its component tree. Scene components can be attached to one another, forming a transform hierarchy inside the Actor.

Components are the unit of reuse:

- `UStaticMeshComponent` — renders a static mesh. The workhorse of archviz.
- `UInstancedStaticMeshComponent` (ISM) and `UHierarchicalInstancedStaticMeshComponent` (HISM) — many transforms of one mesh in one draw call. See file `08`.
- `UDirectionalLightComponent`, `USkyLightComponent`, `UPointLightComponent`, `USpotLightComponent`, `URectLightComponent`
- `USkyAtmosphereComponent`, `UExponentialHeightFogComponent`, `UVolumetricCloudComponent`
- `UCineCameraComponent` — the physically-modelled camera used for all archviz output
- `USplineComponent` — paths, roads, cable runs, camera rails

For archviz, the useful mental model is: **a building is a hierarchy of Actors, each holding one or more mesh components, plus a small number of light, camera and volume Actors.** The Datasmith importer builds exactly this.

### The lifecycle you actually care about

For an Actor: constructor (defaults only) → `OnConstruction` / Construction Script (editor-time and spawn-time; runs whenever a property changes in the editor) → `BeginPlay` (gameplay start) → `Tick` (per frame, if enabled) → `EndPlay` → destruction.

The **Construction Script** is the archviz automation hook. It is a Blueprint graph that re-runs every time you move the Actor or change one of its exposed variables in the editor, and it can add components. A parametric fence, a window frame that rebuilds its mullions when you change a width, a room that instances furniture from a data table — all live here. Note it runs in the editor, not just at runtime, and heavy construction scripts make the viewport sluggish.

## The Gameplay Framework

Even a walkthrough uses these classes; understanding them stops you fighting the engine.

- **Game Instance** — created at engine launch, alive until shutdown, not replicated, no physical presence. Anything that must survive a level load lives here. Hosts Game Instance Subsystems.
- **Game Mode** — an Actor created immediately after the level loads, server-authoritative, not persistent across levels, set per map. Defines the rules and spawns the other framework Actors. In archviz this is where you nominate which Pawn the visitor possesses and which Player Controller is used.
- **Game State** / **Player State** — non-physical Actors tracking global and per-player state, replicated between server and clients.
- **Pawn** — an Actor a controller can possess; the visitor's physical presence. `ADefaultPawn` (fly-through) and `ACharacter` (capsule, `UCharacterMovementComponent`, walking/gravity/step-up) are the two archviz choices.
- **Character** — a Pawn specialised for humanoid movement. Use it when the visitor should walk the building at eye height with collision and stairs; use a `DefaultPawn` or a spectator pawn for free-flight review.
- **Player Controller** — the manager that turns input into actions, owns the HUD and the UI input mode, and holds the camera manager. Archviz interaction logic (click-to-teleport, material switcher, measurement tool) is usually best placed here or in a component on it, not on the Pawn.
- **AI Controller** — the non-human equivalent; irrelevant to most archviz except for populating a scene with walking crowds.

**Subsystems** are the modern place for global logic. They are `UObject`s with an automatic lifetime tied to a host: `UGameInstanceSubsystem`, `UWorldSubsystem`, `ULocalPlayerSubsystem`, and — crucially for automation — `UEditorSubsystem`. `unreal.get_editor_subsystem(unreal.EditorActorSubsystem)` in Python is exactly this pattern. Prefer a subsystem to a singleton Actor or a Blueprint function library holding state.

## Worlds, Levels and streaming

- A **World** (`UWorld`) is the container that holds levels and the actors in them. One world is current in the editor at a time; PIE creates additional worlds.
- A **Level** (`ULevel`, a `.umap` asset) is a collection of Actors. Every world has one **persistent level**.
- **Sublevels** are the legacy composition mechanism: additional levels loaded into the persistent level, either always-loaded or streamed by volume or by Blueprint. Still perfectly valid and often the right answer for a building split into "shell / interior / furniture / landscape" or into per-storey levels.
- **Level Instances** let you place a level asset as a single Actor with a transform — the correct tool for repeating an apartment unit, a housing type, or a standard bathroom pod across a site.

### World Partition

World Partition is UE5's automatic, distance-based data management and streaming system. Instead of hand-authoring sublevels, the world is stored as **a single persistent level divided into grid cells**, streamed by distance from a streaming source. It works with four companion features:

- **One File Per Actor (OFPA)** — each Actor is serialised to its own file rather than into the `.umap`. This is what makes multi-user work on one level possible without constant lock contention. It is also why a World Partition level produces thousands of small files, which matters for source control choice (file `02`).
- **Data Layers** — logical, runtime-togglable groupings of Actors. In archviz these map naturally onto design options, construction phases, furniture sets and services.
- **Level Instancing** — as above.
- **World Partition HLOD** — automatically generated hierarchical proxies for distant cells.

World Partition is enabled by creating a level from the **Open World** template (`File > New Level > Open World`), by using a Games-category project template, or by converting an existing level via `Tools > Convert Level` or the commandlet:

```
UnrealEditor.exe MyProject -run=WorldPartitionConvertCommandlet MyMap.umap -AllowCommandletRendering
```

Useful commandlet arguments: `-SCCProvider=None` (run without source control), `-ConversionSuffix` (appends `_WP`, leaving the source level intact), `-ReportOnly`, `-DeleteSourceLevels`, `-FoliageTypePath=[Path]`.

Note that grid-cell streaming can be switched off independently: `World Settings > Enable Streaming`. Several templates ship with World Partition on but streaming off. **For a single residential building this is usually the right configuration** — you get OFPA and Data Layers without the complexity of runtime cell streaming. Turn streaming on for a whole site or a masterplan.

The Open World default map ships with a 2 km × 2 km landscape, a landscape material, and a full outdoor lighting rig (sky atmosphere, sky light, directional light, exponential height fog, volumetric clouds).

## Assets and the Content Browser

An **asset** is a `UObject` saved into a package (`.uasset`). The Content Browser is a view over the asset registry. Paths are virtual, not filesystem paths:

- `/Game/...` maps to your project's `Content` folder
- `/Engine/...` maps to engine content
- `/PluginName/...` maps to that plugin's `Content` folder

Asset path forms you will meet in scripts (all equivalent ways of naming the same thing):

```
StaticMesh'/Game/MyFolder/MyAsset.MyAsset'   (reference / text path)
StaticMesh /Game/MyFolder/MyAsset.MyAsset    (full name)
/Game/MyFolder/MyAsset.MyAsset               (path name)
/Game/MyFolder/MyAsset                       (package name)
```

Directory paths may be written `/Game/MyNewFolder/` or `/Game/MyNewFolder`. Any destination folder you pass to an importer **must start with `/Game/`**.

The **Derived Data Cache (DDC)** stores compiled shaders, built Nanite data, distance fields and lightmaps keyed by content hash. A shared DDC on a network path is the single highest-leverage productivity change for a team, and Epic specifically calls it out as important when a project has many Nanite assets.

## Editor versus runtime — the distinction that governs automation

This boundary decides what tool you can use for a given job:

| | Editor | Runtime (PIE, standalone, packaged) |
|---|---|---|
| Python | **Yes** | **No** |
| Blueprint | Yes (Editor Utility Blueprints/Widgets, Blutilities) | Yes |
| C++ | Yes (editor modules) | Yes (runtime modules) |
| Remote Control API | Yes | Yes, if launched with `-RCWebControlEnable -RCWebInterfaceEnable` |
| MCP server | Yes (editor plugin) | Possible in cooked builds only via explicit `IModelContextProtocolModule::StartServer()` |
| Editor Utility Widgets | Yes | No |
| UMG runtime widgets | Yes (in PIE) | Yes |

Epic states it plainly: the Python environment exists **only in the Unreal Editor**, not in Play In Editor, Standalone Game or a cooked executable. Python is a pipeline and automation language, not a gameplay scripting language. Blueprint nodes that execute Python (`Execute Python Script`, `Execute Python Command`) are available only in editor-only Blueprint classes such as Editor Utility Widgets and Editor Utility Blueprints.

For an agent-driven archviz workflow this means: **build the scene with Python in the editor, deliver interactivity with Blueprint or C++.**

## Naming and prefix conventions in code

| Prefix | Applies to |
|---|---|
| `U` | `UObject`-derived classes that are not Actors |
| `A` | `AActor`-derived classes |
| `F` | Plain structs and non-`UObject` classes |
| `I` | Interface classes |
| `E` | Enums |
| `T` | Templates |
| `b` | Boolean variables (`bIsVisible`) |
